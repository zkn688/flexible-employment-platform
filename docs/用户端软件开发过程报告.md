# 某市灵活就业管理服务平台用户端软件开发过程报告

## 一、项目背景与任务说明

### 1.1 项目背景

随着灵活就业形式的发展，越来越多劳动者通过兼职、临时用工、远程办公、项目制工作等方式参与就业。传统就业服务系统主要面向固定岗位和单位招聘，在岗位匹配、灵活用工信息发布、简历投递、政策申报、社保服务和消息沟通等方面难以满足灵活就业人员的综合服务需求。
本课题设计并实现“某市灵活就业管理服务平台”，平台分为用户端、企业端和管理员端三个部分。其中本人主要负责用户端的分析、设计与实现。用户端面向普通灵活就业人员，提供注册登录、岗位浏览、岗位推荐、AI 岗位匹配分析、AI 简历优化建议、AI 模拟面试、岗位收藏、简历管理、岗位投递、投递进度查看、政策申报、社保服务、电子合同查看、消息中心、头像上传、申报材料上传和个人资料维护等功能。

### 1.2 项目目标

用户端建设目标如下：

```text
1. 为灵活就业人员提供统一的线上服务入口。
2. 支持用户维护个人信息、简历和求职偏好。
3. 支持用户浏览、筛选、收藏和投递灵活就业岗位。
4. 支持基于求职偏好的岗位推荐，提高岗位匹配效率。
5. 支持基于 DeepSeek 大模型的 AI 岗位匹配分析，生成匹配度、匹配理由和提升建议。
6. 支持基于 DeepSeek 大模型的 AI 简历优化建议，帮助用户完善简历内容。
7. 支持基于 DeepSeek 大模型的 AI 模拟面试，生成面试题并评价用户回答。
8. 支持头像上传、政策申报材料上传和社保申请材料上传。
9. 支持用户查看公告政策并提交政策申报。
10. 支持用户提交社保参保申请、查看缴费账单并模拟缴费。
11. 支持用户查看电子劳动合同和站内消息。
12. 与企业端、管理员端基于同一数据库实现数据联动。
```

## 二、需求分析

### 2.1 用户角色分析

本系统用户端的主要使用者为普通灵活就业人员。该角色具有以下特点。
```text
1. 需要浏览平台发布的灵活就业岗位。
2. 需要根据个人条件设置求职偏好。
3. 需要维护个人简历并向企业投递岗位。
4. 需要查看企业对投递记录的处理状态。
5. 需要获取平台公告、就业资讯和政策信息。
6. 需要进行政策申报、社保参保申请和缴费查询。
7. 需要与企业或管理员进行站内消息沟通。
```

用户端不负责企业账号管理和管理员业务管理。企业端负责岗位发布、投递处理和合同生成；管理员端负责公告政策维护、岗位审核、政策审核和社保审核等管理功能。

### 2.3 非功能需求分析

#### 2.3.1 易用性需求
系统采用左侧菜单加内容区的后台式布局，用户可以快速进入各功能模块。表单、表格、状态标签、筛选控件和按钮均采用 Element Plus 组件实现，保证界面风格统一。

#### 2.3.2 可维护性需求
前端按照页面、路由、接口请求、布局组件等方式组织代码；后端按照 Controller、Service、Mapper、Entity 分层组织代码，便于后续扩展企业端和管理员端。

#### 2.3.3 数据一致性需求
用户端、企业端和管理员端使用同一套 MySQL 数据库结构。用户端读取的岗位、公告、政策、合同、投递状态等数据，均来自统一数据库，保证三端联动。为解决多人联调时必须处于同一局域网、依赖单台电脑数据库的问题，系统也支持连接 TiDB Cloud 云数据库，使三端后端可以远程访问同一份数据。

#### 2.3.4 安全性需求
用户登录后，后端生成 JWT 登录凭证，前端在请求头中携带 `Authorization: Bearer token`，后端解析 JWT 获取当前用户 ID，避免用户访问其他用户的数据。JWT 中包含用户 ID、角色和过期时间，并通过签名防止 token 被随意伪造。课程设计阶段密码采用明文存储，后续可扩展为 BCrypt 加密。

#### 2.3.5 可扩展性需求
系统已实现头像上传、政策申报材料上传和社保申请材料上传，文件优先上传到阿里云 OSS 对象存储，数据库保存文件访问地址；当 OSS 未配置或上传失败时，后端会自动回退到本地上传目录，保证演示流程稳定。同时，岗位推荐采用规则匹配与 AI 分析结合的方式，后续可根据用户浏览、收藏、投递行为进一步扩展推荐算法。

### 3.3 业务流程总体设计

#### 3.3.1 求职业务流程

```text
用户注册/登录
  ↓
完善个人资料
  ↓
设置求职偏好
  ↓
查看推荐岗位
  ↓
浏览岗位详情
  ↓
收藏岗位或投递岗位
  ↓
选择个人简历
  ↓
提交投递
  ↓
查看投递进度
```

#### 3.3.2 岗位推荐流程

```text
用户保存求职偏好
  ↓
系统读取行业、岗位、城市、类型、薪资范围
  ↓
根据岗位名称、描述、要求、行业、城市、类型、薪资计算匹配分数
  ↓
按照匹配分数和发布时间排序
  ↓
返回推荐岗位和匹配理由
```

#### 3.3.3 AI 岗位匹配分析流程

```text
用户进入岗位详情
  ↓
点击 AI 匹配分析
  ↓
后端根据 token 获取当前用户 ID
  ↓
查询用户求职偏好、简历信息和岗位信息
  ↓
后端拼接 Prompt 并调用 DeepSeek API
  ↓
DeepSeek 返回匹配度、匹配理由和提升建议
  ↓
前端以侧边抽屉形式展示 AI 分析结果
```

如果 DeepSeek API 未配置、网络异常或调用失败，后端会自动切换到基于规则的匹配结果，保证系统功能可用。

#### 3.3.4 政策申报流程

```text
用户查看政策
  ↓
进入政策详情
  ↓
填写申请人、联系电话
  ↓
上传政策申报材料
  ↓
提交政策申报
  ↓
管理员审核
  ↓
用户查看审核结果
```

#### 3.3.5 社保服务流程

```text
用户填写社保参保申请

上传社保申请材料

提交申请
  ↓
管理员审核
  ↓
用户查看申请状态
  ↓
管理员生成缴费账单

```

#### 3.3.6 AI 模拟面试流程

```text
用户进入 AI 面试页面
  ↓
选择岗位方向和面试难度
  ↓
后端调用 DeepSeek API 生成模拟面试题
  ↓
用户选择题目并输入回答
  ↓

  ↓
```

如果 DeepSeek API 未配置或调用失败，后端自动使用规则面试题和规则评价结果，保证演示流程稳定。

#### 3.3.7 文件上传流程

```text
用户选择头像或申报材料文件
  ↓
前端使用 multipart/form-data 上传文件
  ↓
后端校验文件类型和大小
  ↓
后端优先上传到阿里云 OSS
  ↓
返回 OSS 公开访问地址
  ↓
如果 OSS 未配置或上传失败，则回退保存到 E:\keshe\uploads 目录
  ↓
返回 /upload/... 本地文件访问路径
  ↓
数据库保存文件访问地址，页面可通过该地址查看头像或材料
```

### 3.5 前端总体设计

前端采用 Vue 3 单页应用模式，主要结构如下：

```text
frontend/src
├─ api                  接口请求封装，包括用户、岗位、简历、AI、社保等接口
├─ constants            前端常量，如岗位选项
├─ layouts              用户端主布局
├─ router               路由配置
└─ views/user           用户端页面
```

前端页面统一放在 `views/user` 目录下，接口请求统一封装在 `api` 目录下，避免在页面中直接书写后端地址。

### 3.6 后端总体设计

后端采用 Spring Boot 分层结构。
```text
Controller 层：接收前端请求，处理参数和返回结果
Service 层：封装业务逻辑
Mapper 层：负责数据库访问
Entity 层：映射数据库表
Common 层：统一返回结果和异常处理
Utils 层：Token 解析等工具方法
```

### 4.1 注册登录模块详细设计

#### 4.1.1 页面设计

用户注册页面提供用户名、密码、确认密码、真实姓名、手机号、邮箱、性别等输入项。登录页面提供用户名和密码输入框。

#### 4.1.2 接口设计

| 功能 | 请求方式 | 接口 |
|---|---|---|
| 用户注册 | POST | `/api/user/register` |
| 用户登录 | POST | `/api/user/login` |

注册逻辑。
```text
1. 校验用户名、密码、真实姓名、手机号不能为空。
2. 校验用户名是否已存在。
3. 新增用户记录，默认 status = 1。
4. 返回注册成功信息。
```

登录逻辑。
```text
1. 根据用户名、密码和 status = 1 查询用户端
2. 查询成功后生成 JWT token。
3. 返回用户 ID、用户名、真实姓名、手机号、JWT token。
4. 前端保存 token 和用户信息。
```

JWT 认证流程。
```text
1. 用户登录成功后，后端使用密钥生成 JWT。
2. JWT 中写入用户 ID、角色、签发时间和过期时间
3. 前端将 JWT 保存到 localStorage。
4. Axios 请求拦截器在请求头中加入 Authorization: Bearer token。
5. 后端接口通过 TokenUtils 解析 JWT，获取当前用户 ID。
6. 如果 token 缺失、过期或签名校验失败，则提示用户重新登录。
```

#### 4.14.1 存储方式设计

```text
https://your-oss-bucket-name.oss-cn-beijing.aliyuncs.com/avatar/user-1-xxx.png
https://your-oss-bucket-name.oss-cn-beijing.aliyuncs.com/materials/material-1-xxx.pdf
```

OSS 配置位于后端 `application.yml`。
```yml
aliyun:
  oss:
    enabled: true
    endpoint: oss-cn-beijing.aliyuncs.com
    bucket-name: your-oss-bucket-name
    access-key-id: ${ALIYUN_OSS_ACCESS_KEY_ID:}
    access-key-secret: ${ALIYUN_OSS_ACCESS_KEY_SECRET:}
```

其中 AccessKey 通过环境变量读取，不直接写入代码或配置文件。后端上传逻辑会先判断 OSS 是否启用且配置完整，再调用 OSS SDK 上传文件。
当 OSS 配置不完整、网络异常或上传失败时，系统自动回退到后端本地目录：

```text
E:\keshe\uploads
```

目录结构。
```text
uploads
├─ avatar       用户头像
└─ materials    政策和社保申报材。
```

后端通过 Spring MVC 静态资源映射将 `/upload/**` 映射到上传目录，使前端可以通过返回路径访问文件。

上传成功后，后端返回文件访问地址。启用 OSS 时返回 HTTPS 地址，例如：

```text
https://your-oss-bucket-name.oss-cn-beijing.aliyuncs.com/avatar/user-1-xxx.png
https://your-oss-bucket-name.oss-cn-beijing.aliyuncs.com/materials/material-1-xxx.pdf
```

```text
/upload/avatar/user-1-xxx.png
/upload/materials/material-1-xxx.pdf
```

数据库只保存文件访问地址，不直接保存文件二进制内容。该方式既能利用 OSS 减少本地磁盘依赖，也能在 OSS 异常时通过本地存储保证课程设计演示可用。

## 八、系统实现特点

### 8.1 基于规则的岗位推荐
系统根据用户求职偏好进行岗位推荐，匹配字段包括：

```text

期望行业
期望城市
岗位类型
薪资范围
```

系统为每个可用岗位计算匹配分数，并将匹配度返回前端展示。首页推荐岗位卡片显示匹配度进度条和匹配理由，使推荐结果更直观、更具可解释性。

### 8.2 DeepSeek AI 智能求职辅助

用户端接入 DeepSeek 大模型，形成“AI 简历优化 + AI 岗位匹配分析 + AI 模拟面试”的智能求职辅助流程。
```text

  ↓

```

该功能使用户端不只是提供岗位浏览和投递，还能为用户提供投递前的智能分析和求职指导。

#### 8.2.1 AI 岗位匹配分析

用户端在岗位详情页接入 DeepSeek 大模型，实现 AI 岗位匹配分析。系统会综合以下信息生成匹配结果。

```text
岗位行业
岗位类型
岗位城市
薪资范围
岗位描述
岗位要求
```

AI 返回内容包括：
```text

提升建议
```

### 8.6 文件上传能力

系统实现了头像上传和申报材料上传，提升了用户端表单的真实性和完整性。
```text

材料上传 → 保存到 uploads/materials → policy_apply/social_security_apply 保存访问路径
```

文件上传功能支持后端本地存储和阿里云 OSS 两种方式。配置 OSS AccessKey、Bucket、Endpoint 后，头像和材料会上传到阿里云 OSS；如果 OSS 未配置或上传失败，系统会自动回退到本地文件存储，保证课程设计演示流程可用。
阿里云 OSS 配置如下。
```yml
aliyun:
  oss:
    enabled: true
    endpoint: oss-cn-beijing.aliyuncs.com
    bucket-name: your-oss-bucket-name
    access-key-id: ${ALIYUN_OSS_ACCESS_KEY_ID:}
    access-key-secret: ${ALIYUN_OSS_ACCESS_KEY_SECRET:}
```

其中 AccessKey 通过环境变量配置，不直接写入代码或配置文件，避免密钥泄露。

### 8.7 Redis 缓存层
系统引入 Redis 作为缓存组件和临时数据存储组件。一方面缓存用户首页中访问频率较高、短时间内变化不频繁的数据，减少对 TiDB Cloud 云数据库的重复查询；另一方面保存登录和注册图形验证码，利用 Redis 自动过期能力控制验证码有效期。
当前 Redis 使用内容包括：
```text
1. 用户推荐岗位结果：缓存 key：user:recommend:{userId}:{pageNum}:{pageSize}，有效期 10 分钟。
2. 公告列表：缓存 key：content:notices:enabled，有效期 5 分钟。
3. 政策列表：缓存 key：content:policies:enabled，有效期 5 分钟。
4. 登录/注册验证码：缓存 key：captcha:user:{scene}:{captchaId}，有效期 5 分钟。
```

用户修改求职偏好后，系统会删除该用户首页常用分页的推荐岗位缓存，使后续访问可以重新根据最新偏好计算推荐结果。
Redis 不保存核心业务数据，核心数据仍持久化到 TiDB Cloud。后端通过 `RedisCacheService` 封装缓存读取、写入和删除逻辑；如果 Redis 缓存读写失败，岗位推荐、公告和政策列表会自动回退为直接查询 TiDB Cloud。验证码由 `CaptchaService` 生成，验证码答案保存到 Redis，校验成功后立即删除，防止验证码重复使用。
后端 Redis 配置如下。
```yml
spring:
  redis:
    host: ${REDIS_HOST:localhost}
    port: ${REDIS_PORT:6379}
    database: ${REDIS_DATABASE:0}
    timeout: 1s

app:
  redis-cache:
    enabled: ${REDIS_CACHE_ENABLED:true}
```

该设计使 Redis 既能提升热点数据访问速度，也能承担验证码这类临时安全数据的存储工作。

### 8.8 JWT 登录认证机制

系统采用 JWT 实现用户端登录认证。用户登录成功后，后端生成带签名的 JWT，并返回给前端。前端后续请求通过 `Authorization` 请求头携带 JWT，后端解析 token 获取当前用户 ID，从而保证用户只能访问自己的简历、投递记录、合同、消息、社保申请等数据。
JWT 认证机制特点：
```text
1. token 中包含用户 ID、角色和过期时间。
2. token 通过密钥签名，避免被随意伪造。
3. 前端统一通过 Axios 请求拦截器携带 token。
4. 后端统一通过 TokenUtils 解析 token。
5. token 过期或校验失败时提示用户重新登录。
```

该设计相比简单字符串 token 更规范，也便于后续扩展用户端、企业端、管理员端的角色权限控制。




## 十一、后续补充记录

### 11.1 Knife4j 接口文档补充说明

项目后端已集成 Knife4j / Swagger 接口文档工具，用于对用户端后端接口进行统一展示、说明和在线调试。Knife4j 页面相当于后端接口的“说明书 + 在线测试工具”，能够清晰展示每个接口的请求路径、请求方式、请求参数、返回结构和接口分组，便于前端开发、后端自测和三端联调。

在本项目中，Knife4j 主要用于展示用户端相关接口，左侧按照 Controller 进行分组，例如：

```text
user-auth-controller              登录、注册、验证码接口
user-job-controller               岗位列表、岗位详情、岗位推荐接口
user-application-controller       岗位投递、投递记录、撤回投递接口
user-resume-controller            简历新增、修改、删除、查询接口
user-upload-controller            头像上传、材料上传接口
user-social-security-controller   社保申请、缴费账单接口
user-ai-controller                AI 岗位匹配、AI 简历优化、AI 模拟面试接口
```

Knife4j 的访问地址如下：

```text
IDEA 本地启动：http://localhost:8080/doc.html
Docker 启动：http://localhost:18080/doc.html
```

在三端联调过程中，Knife4j 可以用来快速判断接口是否正常。例如用户端登录、获取验证码、投递岗位、上传材料等功能出现问题时，可以先在 Knife4j 页面直接测试对应接口。如果 Knife4j 调用接口成功，说明后端接口本身基本正常，问题更可能出现在前端请求地址、请求参数或 token 携带方式上；如果 Knife4j 调用失败，则可以根据返回结果定位后端业务逻辑、数据库数据或 Redis、OSS、DeepSeek 等外部服务配置问题。

对于需要登录的接口，可以先通过登录接口获取 token，再在 Knife4j 页面点击 `Authorize`，填写：

```text
Bearer 登录后返回的token
```

配置完成后，再测试简历、投递、合同、消息、社保等需要身份认证的接口。该方式减少了手动编写 Postman 请求或临时调试代码的时间，提高了联调效率，也方便课程设计答辩时展示后端接口体系。
